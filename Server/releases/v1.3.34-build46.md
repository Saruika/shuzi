## 本次修复

- App 在首次启动、系统通知权限仍未决定时请求授权。允许通知后仍须完成登录与
  账号资料；启动同意只供第一个合格账号消费，之后换号不能继承。用户原来明确
  关闭通知或拒绝系统权限时保留其选择，不重复弹窗。
- App 保持 APNs 令牌在易失内存，通过当前粉丝会话重新登记；短暂失败可以恢复
  登记，不能把已取得系统权限但未完成服务端绑定显示成已经可接收推送。
- 服务端修复旧普通会话未保存 `scope` 时，正常登录成功但推送绑定的新鲜会话
  复核/旧安装初始化拒绝该会话的问题。仅缺失字段按既有普通会话语义归一为
  `normal`；显式 `null`、空值、数组与受限 scope 仍失败关闭。会话过期、安装、
  身份、凭据代次和后来会话优先规则均保持原检查。
- 更早版本缺少 `createdAt` / `sessionID` 的会话无法证明推送安装归属，明确返回
  `fan_session_invalid` / HTTP 401，要求重新登录；不补造安全字段、不将其误报为
  被另一会话取代。真实数据库读取失败仍返回 503，后来正常会话优先仍返回 409。
- 保留 Build 42 的 v3 与 Build 45/46 的 v4 同意版本过渡白名单；推送 schema
  仍为 v3，不改表，不改 APNs 密钥、定时器或主备职责。

## 发布包与部署顺序

发布包只包含 `shuzijun-app-content.php`、`composer.json`、`composer.lock`、
`vendor/` 与 `release.sha256`。清单逐一列出前四项中的全部普通文件，以相对路径
按字节序排序，每行格式为 `SHA256`、两个空格、相对路径、换行。清单自身不列入
清单。发布前运行 `app-content-release-contract-test.py` 独立从源码重算并核验
以上全部固定值。macOS 打包设置 `COPYFILE_DISABLE=1`，避免 AppleDouble 附加文件。

两台服务器固定暂存路径：

```text
/var/lib/shuzijun-app-content/releases/v1.3.34-build46-server-1.5.12.2
```

传输后核对完整包清单、候选入口及模块哈希，并先将以上固定哈希的发布器安装到
`/usr/local/sbin/deploy-app-content-release`（root 所有、不可被普通用户写入）。
两节点已具备完整 live release，使用普通发布器，不运行 legacy bootstrap 或 seeder。

先在备用节点运行以下三步，三步的 bundle 与 hash 必须相同；包预检不接受角色参数，
dry-run 与 apply 的角色必须一致：

```bash
sudo /usr/local/sbin/deploy-app-content-release \
  --bundle /var/lib/shuzijun-app-content/releases/v1.3.34-build46-server-1.5.12.2 \
  --manifest-sha256 c4ac813f68d94ed7a1300aa61e945bbfc1833cc53ea8070b2b9d6f9c1f1a1dae \
  --bundle-preflight
sudo /usr/local/sbin/deploy-app-content-release \
  --bundle /var/lib/shuzijun-app-content/releases/v1.3.34-build46-server-1.5.12.2 \
  --manifest-sha256 c4ac813f68d94ed7a1300aa61e945bbfc1833cc53ea8070b2b9d6f9c1f1a1dae \
  --authority-role standby --dry-run
sudo /usr/local/sbin/deploy-app-content-release \
  --bundle /var/lib/shuzijun-app-content/releases/v1.3.34-build46-server-1.5.12.2 \
  --manifest-sha256 c4ac813f68d94ed7a1300aa61e945bbfc1833cc53ea8070b2b9d6f9c1f1a1dae \
  --authority-role standby --apply
```

备用节点验证完成后，在上海主节点重复三步，仅将 dry-run/apply 角色改为 `authority`。每个节点
核对 live manifest 与所有 payload、PHP-FPM/Nginx 及受保护接口健康。主节点继续独占
Outbox Worker；备用节点保持禁用。以旧缺失 scope 的正常会话和显式受限/畸形 scope
负向夹具验收本次兼容边界，不能只用重新登录后生成的新会话代替旧会话回归。

运行期 `shuzijun-internal-health` 只记录当前 App Content 哈希，不固定 App 插件版本；
webroot/authority verifier 也无插件版本 pin，因此本轮无须重新部署健康监控。历史
`deploy-shuzijun-health-monitor` 仍固定其 Build 42.10 的验收值，今后重新发布健康监控
时须单独更新审核该发布器，不能直接用于本次插件版本。

App 首次授权测试必须使用新建模拟器，普通全量复用构建产物但排除该专项；详见
`TESTING.md`。完成 TestFlight 安装、允许通知、合格账号登录及设备绑定后，才能用
指定测试账号验证生产 APNs 实际送达；系统弹窗成功不能代替送达验收。
