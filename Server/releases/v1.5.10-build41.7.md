## 受控升级事务

本次是升级分支，不是首次安装：三个旧目标必须都存在且必须分别
精确符合上述旧哈希/metadata；health timer 必须预先为
`enabled+active`，否则在零 final 写入时中止。旧 `status.json` 也必须
存在且为 `root:root 0600` regular、non-link、nlink=1；其父目录
`/var/lib/shuzijun-health` 必须为 `root:root 0700` 实目录，并复验
`/var/lib` 和 `/var` 的 root-owned、不可被非 root 写入安全边界；这些 lstat
检查必须在备份 status 之前完成。因此本次事务
没有 status-absent 分支；其 SHA 在 disable/stop 后的 committed backup 内动态冻结。

1. 先在唯一的 `root:root 0700` stage 内预检三个 runtime 文件的 regular、
   non-link、nlink=1、root-only metadata 与精确 SHA-256；执行无 pyc 落盘的
   Python compile 与目标 Linux `systemd-analyze verify`。拒绝任一 final
   symlink/mask、非空 DropInPaths 或不安全父目录。
2. 获取专用锁后，在锁内完整重跑第 1 步、旧 final/status 哈希与
   metadata、DropInPaths 及 timer enabled+active 检查；不允许使用锁外
   预检结果越过 TOCTOU 窗口。冻结旧 timer/service 状态并立即安装
   分阶段 `ERR/INT/TERM/HUP` rollback trap。在首个 systemd 状态变更之前，
   先创建并验证唯一 `root:root 0700` transaction/backup 目录；把旧状态、
   三 final 哈希/metadata 与事务标识写入该目录的 root-only `PREPARED`
   journal，对 journal/事务目录/父目录 `sync -f` 并复验。然后才
   `disable --now` timer、停止 health service，复验两者 inactive；不启停
   Nginx、PHP-FPM、MySQL、sync、failover 或 CDN。
3. disable/stop 完成后、备份前，再次 lstat 并复验 status 目录/父边界和
   `status.json` metadata，然后在第 2 步的同一事务目录中保存
   script/service/timer 与旧 `status.json` 的字节、owner、mode、presence 和哈希。manifest、
   备份目录及其父目录全部 `sync -f` 并复验后，写入 root-only
   `COMMITTED` marker 并再次对 marker/目录/父目录 `sync -f`，才进入
   committed backup phase。此前 trap 只恢复旧 timer enabled/active 语义并保持
   oneshot health service stopped/inactive；此后才
   允许恢复文件。
4. 按已验证角色只处理 common `/var/log/tencent-snapshot.log` 与角色日志：
   authority 为 `/var/log/wp-sync.log`，standby 为
   `/var/log/shuzijun-sync-receiver.log`。存在项必须先 lstat 为 root 所有、
   regular、non-link、nlink=1 且 `/var/log` 边界安全，然后用
   已验证的 `/var/log` dirfd 配合 `openat(O_NOFOLLOW)`，再用
   `fstat/fchown/fchmod` 只原地改为 `root:root 0600`；
   最后要求 path inode 仍与 fd 一致且 inode/mtime 不变。禁止创建、截断、替换或
   `touch` 日志，缺失项保持缺失并进入 degraded。这项单调安全收紧
   不随 monitor 回滚而放宽。
5. timer 全程 disabled/inactive；固定按 script→service→timer 顺序，在每个
   final 的同文件系统父目录创建唯一临时文件；脚本精确设为
   `root:root 0700`，两个 unit 精确设为 `root:root 0644`，然后
   `sync -f`、复验 SHA，再 rename 原子替换并 `sync -f` 父目录。
   安装后对三个 final 重新校验 SHA/metadata，并再次运行
   `systemd-analyze verify`。
6. `daemon-reload` 后要求 service/timer FragmentPath 精确指向 final、
   DropInPaths 为空、ExecStart 精确为
   `/usr/bin/python3 -I /usr/local/sbin/shuzijun-internal-health`、
   `SuccessExitStatus` 包含 2。timer 仍不启用。
7. 记录旧 status inode/SHA，在单次启动前持久写入并 `sync -f`
   `STATUS_MAY_CHANGE` phase；然后只执行 health service，冻结该次
   systemd `InvocationID`、`ExecMainStartTimestamp`、`ExecMainExitTimestamp`
   与纳秒精度启动墙钟窗口。本次不接受 exit 0；
   必须 `Result=success`、`ExecMainStatus=2`、oneshot 回到 inactive/dead。
   新 `status.json` 的 mtime_ns 必须落在该 invocation 高精度墙钟窗口内；
   `checked_at` 因当前字节使用秒精度向下截断，必须要求其代表的
   一秒桶 `[checked_at, checked_at+1s)` 与 invocation 窗口相交，不能把截断后的
   整秒点直接与纳秒 start 比较。inode 必须与旧值不同且新 SHA 不得
   等于旧 SHA，
   并为 `root:root` regular、
   non-link、nlink=1、`0600`，且 JSON 必须符合上述节点角色、精确
   reason set、manifest/PHP 哈希与无 critical 基线。
8. 所有验收通过后，先只 `start` 仍为 disabled 的 timer，要求 active 且有
   下次触发时间。Persistent timer 可能立即产生新 invocation；必须等待
   health service 结束，再次冻结 InvocationID/status inode/SHA。如果任一值
   变化，必须对最后一次 invocation 的时间窗完整重跑第 7 步的
   metadata、schema、role、精确 reasons、critical 与 App 哈希验收；如未变化
   则要证明 timer 尚未触发。不允许只凭 `Result=success` 放行。
   验收后持久写入含最终 InvocationID/status inode/SHA 的 root-only `ACCEPTED`
   marker 并复验，然后只执行 `enable`（不带 `--now`）已 active 的 timer。
   再次确认 enabled+active 且 InvocationID/status 未变；若恰逢正常调度而改变，
   等待完成、重跑全套验收并原子刷新 `ACCEPTED`。最后才解除 trap
   并保留备份/journal。

## 回滚与中断安全

committed backup phase 之后的任意失败都先 disable/stop 新 timer/service；
对三个 final 按 manifest 恢复原字节/metadata。只有在已持久化
`STATUS_MAY_CHANGE` 之后且当前 status inode/SHA 与旧值不同时，才原子恢复
本事务已冻结为 present 的旧 `status.json`；如仍完全相同则不重写，避免
无谓改变 inode/ctime。恢复同样使用
同文件系统临时文件、fsync 与原子 rename，然后 `daemon-reload`、复验旧
哈希/metadata，再次执行 `systemd-analyze verify`，恢复上线前
enabled+active timer 语义，并保持 oneshot service stopped/inactive 直到 timer 下次触发。

如果回滚或复验失败，必须保持 health timer disabled、service stopped，
保留完整备份并报告精确路径；绝不扩大到业务服务。SIGKILL 无法由
trap 捕获，人工恢复必须根据同一备份中已持久化的
`PREPARED/COMMITTED/STATUS_MAY_CHANGE/ACCEPTED` 阶段重放对应回滚或完成事务。
`ACCEPTED` 之前 timer 绝不能处于 enabled；它可能在第 8 步为 active+disabled，
该状态不跨重启持久，且 journal 保留精确恢复信息。

本事务不运行数据库/媒体同步，不启用 failover，不修改 DNS、CDN、
Nginx、PHP-FPM、MySQL、WordPress 内容或 App 媒体。
