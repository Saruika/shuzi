## 修复内容

旧健康脚本通过 failover timer 是否启用来推断 primary/backup，无法识别
固定的 `authority`/`standby` marker。备用节点在维护期关闭 failover 后会
被误判为 primary，并错误要求仅上海节点存在的 CDN timer。新脚本只接受
`/etc/shuzijun/account-authority-role` 中的精确角色，并用固定哈希验证器
复核；任何缺失、额外字节、权限或验证器漂移都进入 critical，绝不默认
authority。

同步日志改为按角色选择：authority 只读 sender 日志，standby 只读
receiver 日志；不再允许无关旧日志掩盖陈旧状态。每日同步 freshness 从
错误的 2 小时调整为与 03:30 日计划匹配的 26 小时，同时仍要求 timer、
service result、完成标记、standby generation 与 failover 状态。日志必须为
root 所有、单链接且不可被组或其他用户写入，否则不作为可信健康证据。
每个最近成功标记还必须带有规范 generation：authority 的已签发值不得
低于最近完成值，standby 的已接受值必须与最近应用值精确相等；
因此状态快照回滚或归零不能被旧的成功日志误报为健康。
备用节点还要求 failover state 明确处于 `primary` 路径；即使三个探针
都恢复，只要仍在 `backup` 切换态就会保持 degraded，不会误报正常。

健康快照现在区分：

- `healthy` / exit 0：核心与运维连续性全部正常；
- `degraded` / exit 2：核心服务仍可用，但同步或 failover 等连续性任务缺失；
- `critical` / exit 1：角色、核心服务、路由或 authority CDN 失败。

systemd 明确把 exit 2 视为一次成功完成的“降级快照”，因此不会每五分钟
制造虚假的 failed unit 与 error 日志；真实状态与 reason codes 仍写入
root-only `status.json`。脚本只读系统状态，禁止调用 sender、receiver
ingest，禁止启动、重启或启用任何服务。

## 安装与回滚事务

生产安装必须把脚本与两个 unit 作为同一个事务，不允许逐个
覆盖后直接离开：

1. 上传到唯一的 `root:root 0700` stage，拒绝符号链接、多链接或
   非 root 可写源，按上述四个 SHA-256 验证字节，并在目标 Linux
   节点上执行 Python compile 与 `systemd-analyze verify`。任一目标为
   symlink/mask、存在未知 drop-in 或父目录边界不安全时立即拒绝。
2. 获取专用安装锁，记录 health timer/service 原状态，立即安装
   `ERR/INT/TERM/HUP` 回滚 trap；执行 `disable --now` 隔离 timer 并停止
   health service，确认两者 inactive 后才继续。不启停 Nginx、PHP-FPM、
   MySQL、同步、failover 或 CDN。
3. 在 `/var/backups/shuzijun-health-monitor/<UTC>-<node>-build41.6-<commit>/`
   创建唯一的 root-only 事务备份，保存三个现有目标与 `status.json`
   的字节、所有者、模式和哈希；原本不存在的目标也必须在
   manifest 中标记。备份目录与父目录 `sync -f` 并复验后，才允许
   第一次 final 写入。
   同一节点的角色日志如果是 root 所有、普通单链接文件却可被
   非 root 写入，只原地收紧为 `0600`，不替换 inode、不 `touch`、不改
   mtime；这项单调安全收紧不随 monitor 回滚而重新放宽。
4. 先在每个目标父目录写入同文件系统临时文件，脚本设为
   `root:root 0700`，unit 设为 `root:root 0644`；`fsync`、重新校验
   SHA-256 后用 rename 原子替换，再 `fsync` 父目录。
5. 重新校验三个 final 哈希与 unit；`daemon-reload` 后要求 FragmentPath
   精确指向两个 final、DropInPaths 为空、ExecStart 与 `SuccessExitStatus=2`
   精确匹配，再单次启动 health service。只有 systemd `Result=success`、
   `ExecMainStatus` 为 0 或 2，且 root-only `status.json` 为 schema 2、
   `role_verified=true`、节点角色正确、`critical_reasons=[]`，且 degraded reasons
   与上线前白名单精确一致时才接受。最后才恢复 timer 原先的
   enabled/active 语义，再确认它 active、未 failed 且存在下次触发时间。
6. 任意一步失败都必须在锁内精确恢复三个备份，删除本事务
   新建但原本不存在的目标（仅当其哈希仍精确等于新候选时），
   `daemon-reload`，复验恢复后哈希/unit，并严格恢复原 timer 状态；
   如果精确回滚也失败，立即保留 timer 停止并报告备份路径，不得继续。

上线后当前预期仍是明确的 `degraded`，而不是伪造 healthy：上海缺少安全
的 v3 同步 scheduler，新加坡的 failover timer 与 accepted generation 尚未
恢复。数据库同步和自动切换属于高风险运维，必须先修复/审核同步接收端的
完整回滚，再由操作者单独批准；本热修绝不自动执行这些动作。
