# v1.4.0-ops-sync1 — 自动同步短暂锁冲突修复

范围：服务器运维热修复，不修改 App 版本、页面、推送频率或权限设计；不上传 TestFlight，不重启服务器。

## 原因

2026-09-06（Asia/Shanghai）的生产日志显示：推送 sweep 于 03:31:11.315 启动，03:31:11.851 完成；同步于 03:31:11.410 启动，03:31:11.736 退出。
推送任务在执行期间持有 `site-operation.lock` 的共享锁，同步需要同一 inode 的排他锁。
旧同步脚本 `flock -n 8` 遇到短暂占用立即退出，且每日任务没有再次排程，导致当天同步漏跑。
已用临时锁文件复现该冲突；这不是 SSH 主机公钥、密码或线路故障。

## 修复与边界

- 不移除保护锁。先尝试排他锁，只有确认属于锁争用时才最多等待 60 秒。
- 获锁后继续原有 inode/路径复核；真正的锁错误立即失败，超时返回 75 并记录明确诊断。
- 不修改接收器、批次计数、身份角色、SSH 公钥校验、密钥、数据库或媒体校验规则。
- 独立安装器默认只读 dry-run；`--apply` 仅修改上海 sender 的这一段逻辑，备份旧字节、校验固定摘要并原子替换。安装时暂时停止同步 timer，结束后恢复原状态；不会自行发起同步。
- 正式验收只通过既有 `shuzijun-sync.service` 启动，保留 Nginx preflight 和 systemd 限制；不直接执行 sender。
