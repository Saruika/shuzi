# Hi，梳子 1.3.33 / Build 45.1 服务端热修复记录

该记录用于 Git 标签 `v1.3.33-build45.1`。iOS 版本仍为 `1.3.33 (45)`；服务端
App Content API 升为 `1.5.12.1`。首次将 1.5.12 部署到上海 authority 后，MySQL
8.0.46 拒绝通知表中未转义的保留字列名 `sensitive`。其余四张推送表已建立，schema
版本 option 未推进，推送 Worker 尚未启用，也没有通知被发送。

本热修将数据库物理列改为 `is_sensitive`，REST/Swift 的 `sensitive` 隐私语义保持
不变。schema 升至 v3；在同一命名锁内兼容表不存在、仅旧列、仅新列及两列并存状态，
任一探测、迁移或 `dbDelta` 错误都会失败关闭且不推进 option。发布后条件还会核验五张
表均为 InnoDB、完整列集以及无前缀的关键 PRIMARY/UNIQUE 索引。

## 精确部署顺序

发布包固定为：

```text
/var/lib/shuzijun-app-content/releases/v1.3.33-build45.1-server-1.5.12.1
```

先在 `backup standby` 执行 `--bundle-preflight`、`--dry-run`、`--apply` 并验证；
随后在 `primary authority` 重复相同步骤。普通发布命令为：

```bash
sudo /usr/local/sbin/deploy-app-content-release \
  --bundle /var/lib/shuzijun-app-content/releases/v1.3.33-build45.1-server-1.5.12.1 \
  --manifest-sha256 f4934cbab314142ec8a11e1b1d59aef9d9e986a19be5dda9db5ec42f24122447 \
  --authority-role standby \
  --dry-run

sudo /usr/local/sbin/deploy-app-content-release \
  --bundle /var/lib/shuzijun-app-content/releases/v1.3.33-build45.1-server-1.5.12.1 \
  --manifest-sha256 f4934cbab314142ec8a11e1b1d59aef9d9e986a19be5dda9db5ec42f24122447 \
  --authority-role standby \
  --apply

sudo /usr/local/sbin/deploy-app-content-release \
  --bundle /var/lib/shuzijun-app-content/releases/v1.3.33-build45.1-server-1.5.12.1 \
  --manifest-sha256 f4934cbab314142ec8a11e1b1d59aef9d9e986a19be5dda9db5ec42f24122447 \
  --authority-role authority \
  --dry-run

sudo /usr/local/sbin/deploy-app-content-release \
  --bundle /var/lib/shuzijun-app-content/releases/v1.3.33-build45.1-server-1.5.12.1 \
  --manifest-sha256 f4934cbab314142ec8a11e1b1d59aef9d9e986a19be5dda9db5ec42f24122447 \
  --authority-role authority \
  --apply
```

每个 `--apply` 前必须使用同一参数执行 `--bundle-preflight`。authority 应只在确认
五张表、schema option=3、FPM/Nginx/接口健康后安装并启动 Outbox Worker；standby 的
Worker 必须保持禁用。不得用模拟器替代生产 APNs 真机验收，也不得发送无明确收件人的
测试通知。
