# Hi，梳子 1.3.30 / Build 42.13 健康监控重连与幂等部署修复

该记录随 Git 标签 `v1.3.30-build42.13` 保存。本版只修复 Build 42.10
健康运行时的部署器；线上运行时、systemd service/timer、快照计划、
App Content 和页面内容字节均不变。因此生产固定路径、阶段目录与
`RELEASE_ID` 继续使用 `build42.10`，42.13 是对该冻结候选的安装器热修。

## 根因与修复

- 两台生产节点已经把腾讯云快照从 root crontab 迁移到
  `/etc/cron.d/tencent-daily-snapshot`。旧部署器仍硬性要求每次都从
  root crontab 删除一行，重试时因实际删除数为零而回滚。
- 新门禁同时接受两种精确状态：尚未迁移时只能删除一条固定旧任务；
  已迁移时必须确认 root crontab 未再包含旧任务，且唯一生产者是
  所有者、权限、单硬链和 SHA-256 全部精确的受管 cron 文件。
- `systemctl disable --now` 之后，inactive oneshot 可能被 systemd 回收；
  随后的 `stop` 因“单元未加载”返回 5 并不代表服务仍在运行。
- 新部署器仅容忍 `stop` / `reset-failed` 的返回码 0 或 5，随后重新
  加载精确验证的 unit 文件，并要求连续两次得到
  `loaded / inactive / dead / no-job / NeedDaemonReload=no`。任何活动、
  失败、未知返回码、文件漂移或属性不一致仍会拒绝继续。
- 正向部署和回滚都使用同一隔离合同；`daemon-reload` 后的新旧
  unit 也要经过连续两次完整验证，避免将短暂的 D-Bus 对象窗口误当成稳定状态。

## 验收与发布顺序

1. 通过健康部署器、健康运行时和完整本地质量门禁。
2. 确认签名同步已经结束，临时停止其 timer，但保留持久化时间戳与
   已提交的 generation 7。
3. 先在新加坡 standby 部署并验收，再在上海 authority 重复同一流程。
4. 两节点都确认健康 timer 已启用且活动、service 无残留任务、状态
   schema 与节点角色正确后，才按既有持久化时间戳分别 enable 和 start
   同步 timer；不使用 `enable --now`。

本版不修改 DNS、CDN、防火墙、SSH 权限、同步协议、账号、用户数据或凭据，
也不执行网络攻击或渗透测试。
