# 合作收件箱查询错误恢复

版本记录：`v1.4.0-build2-preflight4`，2026-09-06。服务端候选 1.5.13.2，保留生产硬关闭；没有部署服务器、开启合作服务、修改 App 页面或上传 TestFlight。

## 已复现的问题

`list_collaboration_requests()` 原本先读取列表，再读取总数，最后才检查数据库错误。真实 WordPress 的 `wpdb` 在下一次查询时会重置 `last_error`；失败的列表查询可能变成空数组，而成功的后续 COUNT 抹掉错误。因此服务器会把故障误报成 200 / 空收件箱。

在独立 WordPress 7.1 / MySQL 8.0.46 环境对列表 SELECT 注入合成 SQL 故障，旧源码实际触发断言失败“failed or invalid query must not become an empty successful inbox: rows”。记录失败后才修改源码，没有将原失败结果改写为通过；生产 WordPress 和用户数据没有参与测试。

## 修正

- 带状态筛选和不带筛选的两条路径，均在列表查询完成后立刻核验结果与错误；失败时不再执行会覆盖错误的计数查询。
- COUNT 保留原始返回值并严格核验类型、数字格式及整数范围，避免把 null/无效值转换为正常的 0。
- 真正空列表仍返回正常的 200 / 0；数据库异常返回既有可重试错误。API 成功字段及现有页面内容保持不变。
- 已核对当前粉丝消息箱的对应读取路径：它已有逐次错误检查，本次不改动该路径或通知投递逻辑。
- 同步更新候选发布清单、模块哈希和备用节点播种工具所固定的发布器哈希。上一生产 manifest 仍保持原值；更新发布工具不等于已执行部署。
