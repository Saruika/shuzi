# Build 46.2 服务端热修复：重新登录 HTTP 503

客户端仍为 TestFlight `1.3.34 (46)`，不改变 App 字节、页面或构建号。
服务端 App Content API 升级到 `1.5.12.3`；Git 标签为 `v1.3.34-build46.2`。

## 原因与修复

用户报告重新登录 HTTP 503。旧会话读取正常不能证明新登录写路径正常。
生产数据库的独立临时 InnoDB 表验证：首次 INSERT 返回 1，随后完全相同的
UPDATE 返回 0，更换 session_option_id 的 UPDATE 返回 1。

新会话安装归属函数先 INSERT 成功，再等值 UPDATE，却要求改变行数必须是 1，
因此误判数据库失败，回滚安装记录并撤销新会话，返回 fan_session_unavailable。
旧会话首次初始化推送安装归属也存在相同错误。

- 两处新建分支在锁内核对所有者后，使用已经成功插入的状态，不再重复更新。
- 既有安装交接仍要求 session_option_id 单调推进且 UPDATE 恰好改变 1 行。
- 保留旧通知取消、设备清除、所有权/凭据/有效期复核、锁、事务及失败回滚。
- 不把 UPDATE=0 普遍当作成功，不绕过账号授权，不删除用户，不更改数据库结构。

## 实际 HTTPS 登录验收

发布后，以随机凭据创建一个短命、待审批且无权限的 QA 账号。仅在内存中持有
凭据，通过 App 相同的 `https://shuzijun.com.cn/wp-json/shuzijun/v1` 路径请求，
严格校验 TLS，不使用内部直调代替 HTTP 登录，不触发公共注册、邮件或 APNs。

- 首次 `POST /fan/login`、`GET /fan/session` 均为 200。
- 同安装重新 `POST /fan/login`、新 token 的 `GET /fan/session` 均为 200。
- 新会话确实推动安装的 session_option_id 递增；账号始终 pending / permissions=[]。
- 两个会话分别 `POST /fan/logout` 均为 200；退出后分别读取会话均为
  `401 / fan_session_invalid`，没有把重新登录本身误当作旧 token 必然失效。
- finally 精确清理此次 QA 用户、13 条元数据、1 条安装状态及 2 个会话清理任务。
  用户、元数据、会话、设备、outbox、安装状态、recipients、cron 关联残留均为 0。
  未改动真实用户，未提交假设备令牌，未发送任何邮件或推送。

此验收证明本次登录写路径恢复；不将它描述为已验证真机 APNs 通知送达。
