# Hi，梳子 1.3.30 / Build 42.14 systemd 返回码兼容修复

该记录随 Git 标签 `v1.3.30-build42.14` 保存。本版是 Build 42.13 在
新加坡备用节点真实 systemd 环境中发现的小型兼容热修；只修改部署器
及其合同测试。健康运行时、service/timer、快照 cron、App Content 和
页面内容字节仍不变，生产 `RELEASE_ID`、固定路径与阶段目录仍为
`build42.10`。

## 生产证据与修复

- Build 42.13 在备用节点停用健康 timer 后，`stop` 通过，但该节点的
  `systemctl reset-failed` 对已被回收的 oneshot 返回 `1`，而非其他
  环境观察到的 `5`。
- 失败发生在 `PREPARED` 阶段，尚未写入 `COMMITTED`，也尚未替换健康
  运行时、systemd unit、快照计划或状态文件。现场按旧运行时的固定
  SHA-256 复验后，已恢复 timer 为 `enabled / active / waiting`，并执行
  一次健康检查；节点角色正确且无严重原因。
- 新规则按动作区分：`stop` 仅接受 `0/5`；`reset-failed` 接受
  已在目标系统实测的 `0/1/5`。它们都只是停止意图的返回值，不能代替
  后置验证。
- 只有在 `daemon-reload` 后连续两次通过完整的
  `loaded / inactive / dead / no-job / NeedDaemonReload=no` 以及文件、
  FragmentPath、DropIn、Exec 和角色合同时才能继续。任何其他返回码、
  活动状态、任务残留或漂移仍失败关闭。

## 验收与发布顺序

1. 专项合同必须分别覆盖 `stop=1` 拒绝、`reset-failed=1` 通过，以及
   通过后完整双采样不成立时拒绝。
2. 在不含并行同步 v5 草稿的隔离副本中通过完整本地质量门禁。
3. 再次按 standby 优先部署，验证新运行时、健康 timer、状态 schema、
   节点角色和快照唯一生产者；通过后才部署 authority。
4. 两节点验收后才根据既有持久化时间戳分别 enable、start 同步 timer，
   并确认 generation 仍为 7。

本版不修改 DNS、CDN、防火墙、SSH 权限、同步协议、账号、用户数据或凭据，
也不执行网络攻击或渗透测试。
