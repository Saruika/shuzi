# P0 复现：管理员注销误删已发布相册图片

版本记录：`v1.4.0-build4-review-env-preview28`，2026-09-07（UTC+8）。
本次只新增 opt-in 原生回归和发布阻塞记录，**没有修复或部署生产删除逻辑**。

## 实际复现

在新建 iPhone 17 Pro Max / iOS 26.5 模拟器中，使用 shipping FanAccountStore / AdminSessionStore
连接独立审核 HTTPS 后台，不使用响应替身或界面门禁绕过：

1. 创建临时普通用户，验证抖音必填、待审批禁入，审批后退出并以 HS 身份码/密码重新登录。
2. 为该用户绑定管理员，实际上传两张内存生成的合成 PNG（不是艺人照片），创建临时相册。
3. 通过真实原生客户端把两张图片以反向顺序加入相册，完整内容返回的图片 ID 顺序正确。
4. 撤销管理员后，旧管理员会话立即被拒绝；通过普通用户的主动注销接口删除自己的账号。
5. 独立维护账号再次读取内容：**相册仍存在，图片数从 2 变成 0**。

两轮均以该新增保留断言失败，xcodebuild 退出 65；不能记为通过或仅认为模拟器取消。
最后一轮明确诊断 `album-present=true; image-count=0`。当前 `remove_fan_user` 直接调用
`wp_delete_user($user_id)`，没有重新归属参数；标准 WordPress 删除流程会清理用户所创建的附件。
此行为是在独立审核环境复现，不声称已经观察到生产艺人照片丢失，也没有操作生产账号。

## 清理与验证边界

临时素材按每轮唯一随机标记定位，最多一册两图；删除前验证类型、准确标题及附件文件名。
每轮清理后与原有目录比较：除更新时刻外完整内容摘要一致，原有两本艺人相册没有参与修改。
两次包装器的维护访问码清理遇到 RuntimeError，未把其自动清理状态报告为成功；随后对两轮
各自的精确标记执行受限恢复，并分别独立确认 credentials=0、users=0、fixtures=0，移除相应私有恢复记录。
未重置 Test1/Test2 或其他账号，未删除原有图片，自有模拟器由包装器清理。

新增图片操作仅在明确设置 `YISHU_REVIEW_MEDIA_ACCEPTANCE=1` 的私有测试流程执行。
不把未设置该参数的旧流程通过当作本场景通过；正式二进制未改动。

## 需要的产品决定与后续修复

必须明确管理员注销时“个人账号资料”与“已发布的艺人业务作品”的边界。
建议保留已发布作品并解除个人上传者关联，删除个人账号、会话、推送和其他个人资料；
未发布素材的保留/清理规则也需相应明确。不擅自永久保留本应随用户删除的个人数据，
也不通过禁用用户侧注销来避开问题。确认规则后实现服务端归属/删除处理并重跑本回归。
