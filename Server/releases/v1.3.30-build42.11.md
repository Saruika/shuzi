# Hi，梳子 1.3.30 / Build 42.11 签名同步回执恢复

该记录随 Git 标签 `v1.3.30-build42.11` 保存。本版修复已提交的
generation 7 因旧 receiver 将备份保留路径写入标准输出，导致上海
sender 无法确认成功、服务误报失败的恢复缺口。新版不重传、
不回滚、不重用已消耗的代数，而是通过固定 SSH 公钥与强制命令
通道查询备节点的完整持久状态。

- receiver 新增只读 `--reconcile-receipt`；只有 accepted、active、
  durable commit、active-release、媒体 inode 和运行态全部自洽，且不存在
  未完成事务时，才输出一行规范 v5 回执。
- sender 在发送前持久化 generation、证据、预期发布标识和实际 ingest
  receiver 哈希。内联 ACK 正常、缺失、截断或被污染都只进行
  一次状态查询；NUL、CRLF、多行和超长输出在进入 Bash 变量前
  就被原始字节验证。
- pending 回执删除使用 `.clearing-pending-receipt-v5.<token>` 两阶段墓碑。
  rename、unlink 或目录 fsync 任一处中断都会恢复可见 pending，或由
  下次启动依据已持久的精确授权继续；缺回执、内容冲突、多墓碑、
  符号链接、硬链接或错误权限全部失败关闭。
- 新加静态且不可 enable 的
  `shuzijun-sync-reconcile-generation7.service`，通过正式 Nginx preflight、
  全局 sync lock 和与正常 sender 相同的 systemd sandbox 执行一次
  generation 7 旧回执迁移，不再需要绕过服务直接调用 sender。
- 发布器可原地升级已稳定提交的 generation 7：保留
  `previous-generation-6-for-7`，不重放 bootstrap，不改动媒体、数据库或
  receiver state，并将 standby-first receipt 精确绑定当前第 7 代。

## 生产顺序

1. 保持同步 timer disabled/inactive，先在新加坡 standby 执行发布器
   dry-run/apply，生成并验证 generation 7 `standby-first.receipt`。
2. 将该收据原字节放入上海 primary stage，再执行 authority
   dry-run/apply。
3. 仅通过 `systemctl start shuzijun-sync-reconcile-generation7.service`
   运行一次恢复；验证 pending/墓碑均不存在、resolution 为 v5、
   authority 日志记录 `completion-reconciled generation=7`。
4. 重新验证两节点 generation 7、服务、页面和签名证据；只有全部
   通过后才恢复 timer，启用与启动分开，避免 `Persistent=true` 立即补跑。

不包含 SSH/签名私钥、云 API 密钥、密码、手机号或会话令牌。
